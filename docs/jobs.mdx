# Clarity Jobs

> **Clarity finds jobs. Mention makes jobs social. Employers may pay for
> publishing and tooling, never for ranking.**

Clarity Jobs is a vertical over the existing search platform, not a second
engine. Discovery, crawling, JSON-LD extraction, chunking, embeddings, lexical
and semantic ranking, verified sites, removals and quotas are all the same
machinery documented in [the API reference](api-reference); Jobs adds a
`JobPosting` normalizer, a structured projection, a lifecycle policy, a
conservative dedupe strategy and a typed API.

Every other Oxy product consumes Jobs through `@clarity.surf/sdk`. No product
may run its own crawler, employment extractor, semantic job index or competing
global jobs ranker.

## Ownership

| Owner | Responsibilities |
| --- | --- |
| Clarity | Discovery of public listings, crawl/index lifecycle, `JobPosting` extraction, the normalized projection, dedupe, lexical/semantic/hybrid ranking, structured filters, provenance, expiry, the `clarity.surf/jobs` portal, and the Jobs API/SDK |
| The publisher | The canonical listing itself. Clarity never becomes a second source of truth for an externally authored role |
| Mention and other products | Social distribution, first-party authoring, applications and employer workflow |

Clarity owns no applicant tracking, no CV or candidate store, no application
inbox and no interview state. It indexes public information about openings.

## Naming: `jobs` is employment

The asynchronous crawl/index task used to be called a *job*. It is now an
**index operation**, and `jobs` means employment everywhere:

| Concept | SDK | REST |
| --- | --- | --- |
| Crawl/index work | `clarity.operations.get/cancel/wait` | `GET /v1/operations/:id`, `POST /v1/operations/:id/cancel` |
| Employment listings | `clarity.jobs.search/get/byUrl/ingest` | `POST /v1/jobs/search`, `GET /v1/jobs/:id`, … |

`ResolveResult.jobId` became `operationId`. The internal table is still
`clarity_crawl_jobs`; renaming storage would buy nothing and the public contract
is what was ambiguous. The rename is a clean cut — there is no alias.

## Extraction

`job` is a first-class `DocumentType`. A page whose JSON-LD carries a
`schema.org/JobPosting` — directly, in an array, or inside `@graph` — is
classified as a job document, and `src/search/jobs/extract.ts` normalizes:

title, description, hiring organization (name, URL, logo), employment type,
`datePosted`, `validThrough`, job locations, applicant location requirements,
base salary (currency, min/max, unit), identifier/requisition id, direct-apply
flag, qualifications, responsibilities, skills, education and experience
requirements, industry, occupational category, and the listing/apply URL.

Two rules hold everywhere:

- **Nothing is invented.** A field the source did not state is absent. An
  unmappable `employmentType`, a salary without a currency or a unit, an
  unparseable date — all dropped rather than guessed.
- **Everything carries provenance.** Each normalized field records whether it
  came from JSON-LD (`json_ld`) or from an ingestion payload (`api`), with the
  extraction timestamp, in `field_evidence`.

### Listing text is Markdown

`description`, `qualifications`, `responsibilities`, `educationRequirements` and
`experienceRequirements` are stored and returned as **Markdown** — a CommonMark
subset — so a consumer can show the headings, lists and links the source
published. Every other text field (title, employer name, industry,
occupational category, locations, skills) is plain text.

| Source HTML | Markdown |
| --- | --- |
| `<h1>`…`<h6>` | `#`…`######` heading |
| `<p>`, `<div>` and other blocks | paragraph (blank line) |
| `<br>` / `<br><br>` | hard line break (`\` at end of line) / new paragraph |
| `<ul>`, `<ol start>`, `<li>`, nested | `- item`, `1. item`, indented sub-lists |
| `<strong>`/`<b>`, `<em>`/`<i>` | `**bold**`, `_em_` |
| `<a href="https://…">` | `[text](https://…)` — any other target (`javascript:`, `data:`, relative) keeps only its text |
| `<script>`, `<style>`, `<iframe>`, `<noscript>`, `<svg>`, … | removed with their contents |
| any other tag | removed, text kept |

Entities (named and numeric) are decoded. Text that would otherwise read as
Markdown syntax (`*`, `[`, a leading `#` or `- `) is backslash-escaped, and a
literal `<` is written `\<`, so **no raw HTML ever survives**: the value is safe
for a Markdown renderer with HTML disabled. Plain-text and Markdown input (what
a first-party publisher like Mention sends) passes through with its line
structure: line endings normalized, trailing whitespace trimmed, runs of blank
lines collapsed, bullet glyphs (`•`) written as `-` items. Double-encoded UTF-8
is repaired first. The converter is `src/search/jobs/markdown.ts`; every feed
adapter uses it rather than stripping HTML itself, and it is idempotent, so a
feed listing normalized twice is unchanged.

Converting `<li>` to `- ` is notation, not invention: no word reaches the
Markdown that the source did not publish.

Anything that needs plain text derives it from the Markdown with
`markdownToPlainText` — the lexical `search_vector`, the document text and
chunks used for embeddings, result `snippet`s, the description fingerprint and
the listing-completeness signal (a description counts as substantive when it
carries a fingerprint, i.e. at least 200 characters of folded plain text). Link
targets and syntax are dropped, so the same content fingerprints identically
whether it arrived as HTML, Markdown or plain text.

Rows written before this contract hold plain text, which is already valid
Markdown. Recrawls and feed polls re-project every column of a listing, so they
converge on their own; no backfill is needed.

Workplace type is derived only from explicit structured signals:

| `jobLocationType` | Physical `jobLocation` | Result |
| --- | --- | --- |
| `TELECOMMUTE` | none | `remote` |
| `TELECOMMUTE` | one or more | `hybrid` |
| absent | one or more | `onsite` |
| absent | none | *(unset)* |

Countries resolve to ISO 3166-1 alpha-2 only when the source value is a code or
a recognized country name. Macro-regions (`europe`, `european_union`,
`north_america`, `south_america`, `latin_america`, `africa`, `asia`,
`middle_east`, `oceania`) expand into a documented country list; Clarity never
infers that an unlisted country belongs to a region.

## The projection

`clarity_job_postings` is a **search representation**, keyed
`(document_id, source_key)` and derived from the document it points at. It is
not an ATS and not a second source of truth. Re-crawling converges; it never
appends.

Filterable columns cover employer identity, locations (raw JSON plus country /
region / locality arrays), workplace type, employment types, salary (source
amount, currency and interval, plus an annualized pair used *only* for
cross-interval filtering — Clarity never converts currencies), skills, dates,
status and source provenance. A per-listing `search_vector` gives jobs their own
lexical field; semantic relevance reuses the document's chunk embeddings.

No column in the projection can express a commercial relationship, and the
ranking contract test asserts that.

## Lifecycle

Listings expire faster than ordinary documents, so absence is a signal.

| Status | Cause |
| --- | --- |
| `active` | Seen recently and not past `validThrough` |
| `expired` | The source's `validThrough` has passed |
| `closed` | The source withdrew it: HTTP 404/410, the page no longer carries a `JobPosting`, or a publisher close signal |
| `removed` | The underlying document was removed or blocked |
| `stale` | No declared expiry and not re-observed for **45 days** |

Only `active` is returned by default; expired and closed listings are never
implied. They stay retrievable with an explicit `statuses` filter, and the
portal labels a non-active listing rather than hiding the fact.

The policy is enforced twice: the worker sweeps stored statuses every 15
minutes (and re-queues due job documents for verification on the same cadence,
under the owner that originally requested them), and the same predicate is
re-evaluated at query time so nothing can surface as active between sweeps.

## Canonicalization and deduplication

One opening commonly appears on the employer's careers site, an ATS, a job board
and a first-party product. Clarity groups them and shows one, **without ever
discarding a source**.

Two listings join a cluster only when they share at least one signature:

1. **identifier** — same employer *and* same requisition id.
2. **listing_url** — same listing or apply URL after stripping tracking
   parameters, `www.`, scheme and trailing slash.
3. **content** — same employer *and* normalized title *and* primary location
   *and* description fingerprint.

A similar title is never sufficient on its own. Signatures live in their own
table and clustering only sets `cluster_id`, so a wrong grouping is undone by
deleting signature rows or clearing the column — no listing is destroyed.

URL stability varies by provider — a Recruitee offer's URL is a mutable title
slug with no id anywhere in it, so the same posting can present a different
`listing_url` signature after the employer edits its title. This is exactly
why **identifier** is checked first: every feed adapter that has one populates
it from the provider's own API id rather than the URL, so a slug change alone
never produces a false "new" listing for a provider that supplies an id.

The displayed copy is elected by evidence, not by product: the employer's own
domain first, then a public ATS host, then a Clarity-verified site, then
anything else, tie-broken by first-seen time then id. Every other member is
returned as `otherSources`; `includeDuplicates: true` returns them as separate
results.

## Search

```http
POST /v1/jobs/search
Authorization: Bearer <oxy_sk credential>   # scope clarity:search
```

Free text runs lexical, semantic or hybrid (reciprocal-rank fusion, the default)
relevance, so `frontend engineer working on React Native mobile apps` can match
a role titled *Mobile Software Engineer*. Omitting `query` browses by filters
and freshness. When the embedding route is unavailable, hybrid degrades to
lexical and says so in `degraded`; explicit `semantic` fails with `503`.

Filters: `locations` (country name/code, city, region, or macro-region),
`workplaceTypes`, `employmentTypes`, `employers` (name or domain),
`sourceDomains`, `skills`, `salary` (`min`/`max`/`currency`/`interval`),
`publishedAfter`/`publishedBefore`, `statuses`, `includeDuplicates`, `limit` and
an opaque `cursor`.

Results are complete normalized listings — employer, locations, workplace type,
employment types, salary when stated, dates, status, source and evidence — so no
consumer has to reconstruct a role from a generic snippet.

A credentialed job search draws on the same monthly search quota and per-minute
request rate as `/v1/search`, and answers `429 monthly_quota_exceeded` when the
allowance is spent. Quota is capacity, never relevance.

Other routes: `GET /v1/jobs/:id`, `GET /v1/jobs/by-url?url=…`,
`POST /v1/jobs/:id/report`, `GET /v1/jobs/stats` (corpus health) and
`GET /v1/jobs/capability` (the agent tool descriptor). The unauthenticated
portal surface mirrors the read routes and the report route under `/jobs`.

## Ranking contract

Organic position comes from exactly these signals:

- lexical relevance to the explicit query
- semantic relevance
- freshness
- listing completeness
- duplicate suppression

Structured filters are constraints applied *before* ranking; they narrow the
candidate set and never boost a listing inside it.

These may never influence organic position:

- what an employer paid Mention, Oxy or Clarity
- employer subscription tier, commercial licensing tier or advertising spend
- Mercaria activity or unrelated Mention engagement
- private applicant behaviour or inferred sensitive traits

**There is no `pay more → rank higher` path.** If Jobs is monetized later,
payment may buy tooling, APIs, verified ingestion, crawl quota or employer
workflow — not relevance.

This is enforced structurally, not by convention.
`packages/backend/src/search/jobs/__tests__/ranking-contract.test.ts` fails the
build if a ranking module references a commercial token, imports a table outside
the search set, names a product table in SQL, gains a commercial column, or
carries a viewer identity.

## Abuse and safety

Jobs is a fraud-heavy category, so several mechanisms already narrow the surface:

- removed and blocked documents drop out of the corpus, and their listings
  become `removed`
- duplicate grouping suppresses syndicated and mass-copied bodies
- stale and expired listings leave active results on a documented schedule
- every result names the source domain, so a reader can judge provenance
- a verified domain proves who controls a host, never that a listing on it is
  legitimate — Clarity does not treat verification as a trust signal for content

Readers can report a listing from the portal, or through the API:

```http
POST /jobs/:id/report            # anonymous portal surface
POST /v1/jobs/:id/report         # credentialed, scope clarity:search
{ "reason": "scam", "detail": "Asks for payment up front." }
```

Reasons are `scam`, `already_filled`, `duplicate`, `misleading`,
`discriminatory` and `other`. `clarity_job_reports` deliberately has **no
reporter column** — no user id, no address, no device — and a report is an
operator signal only. Reports are not a permitted ranking input, the ranking
modules cannot reach the table, and the ranking-contract test enforces both.

Not yet built: Clarity has no threat-intelligence blocklist of known scam or
malware URLs, and no detector for suspicious mass-generated listings beyond
duplicate suppression. Neither has a source of truth in this repository today;
treat reports and the removal path as the current controls.

## Privacy

The portal's `/jobs` routes carry no session and no user identity, so searching
or opening a listing cannot disclose a named user to an employer. Clarity stores
no recruiter-facing browsing history, ingests no private application data, and
infers no sensitive traits. Corpus telemetry is aggregate: active listings,
counts by status and source type, salary coverage, grouping and cluster counts —
never per viewer.

## Sources and ingestion

1. **Public web** — any page exposing valid `JobPosting` structured data:
   careers sites, Greenhouse, Lever, Ashby, Workable, other public ATS pages and
   permitted boards. Nothing assumes an ATS.

2. **Registered public feeds** — the supply side. Clarity polls keyless public
   endpoints on their own interval and projects what they return:

   | Kind | Identifier | Endpoint |
   | --- | --- | --- |
   | `greenhouse` | board token | `boards-api.greenhouse.io/v1/boards/<token>/jobs?content=true` |
   | `lever` | company slug | `api.lever.co/v0/postings/<slug>?mode=json` |
   | `ashby` | job board name | `api.ashbyhq.com/posting-api/job-board/<name>` |
   | `workable` | account slug | `apply.workable.com/api/v1/widget/accounts/<slug>` |
   | `recruitee` | company slug | `<slug>.recruitee.com/api/offers/` |
   | `smartrecruiters` | company id | `api.smartrecruiters.com/v1/companies/<id>/postings` |
   | `remoteok` | — | `remoteok.com/api` |
   | `remotive` | optional category | `remotive.com/api/remote-jobs` |
   | `arbeitnow` | — | `arbeitnow.com/api/job-board-api` |
   | `rss` | feed URL | any RSS or Atom job feed |

   **Every one is keyless.** Clarity registers with nobody to read a public
   board, so no source here holds a credential and none may ever be added that
   does — a source needing a key belongs behind an explicit partner agreement,
   not in this table. A registration test asserts no built endpoint carries a
   key, token or secret parameter.

   Sources are **data, not a hardcoded list**: adding a company's board is a row
   through `POST /v1/jobs/feeds`, not a deploy. A malformed identifier is
   rejected at registration rather than silently fetching the wrong board, and a
   failing feed backs off and records the error on its own row instead of
   blocking the others.

   Where a provider's payload happens to embed `schema.org/JobPosting`
   JSON-LD, that is parsed with the SAME extractor a crawl uses. In practice
   the public board APIs above ship their fields directly rather than
   embedded JSON-LD — a live check of Greenhouse and Rippling career *pages*
   on 2026-09-09 found zero `JobPosting` JSON-LD blocks across both (see
   [OxyHQ/Clarity#19](https://github.com/OxyHQ/Clarity/issues/19)), which is
   exactly why the feed path exists: those two providers are reachable through
   Clarity Jobs *only* by a registered board API or feed, never by a generic
   crawl of their hosted page. Every adapter re-expresses its listing as
   `JobPosting` before projection either way, so one normalizer defines every
   field and a listing arriving by feed deduplicates against the same listing
   arriving by crawl instead of racing it. Feed-sourced fields record
   `source: 'feed'` in their evidence.

   The listing's own URL stays its canonical source. Clarity indexes these
   boards; it does not republish them.

   **Rippling** is not yet a supported `kind`: its hosted board
   (`ats.rippling.com/<company>/jobs`) carries no `JobPosting` JSON-LD either,
   and unlike the table above it has no confirmed public, keyless JSON API to
   register as a feed. Adding it needs that endpoint verified first — this
   table has never shipped a guessed one, and it will not start here.
3. **Verified sites** — an employer verifies its careers domain through the
   existing site flow and Clarity keeps it recrawled.
4. **First-party publishers** — a product that just published, updated or closed
   a listing hands it to Clarity instead of waiting for a crawl:

```http
POST /v1/jobs/ingest
Idempotency-Key: <publisher key>
Authorization: Bearer <oxy_sk credential>   # scope clarity:index

{ "url": "https://mention.earth/jobs/7", "jobPosting": { "@type": "JobPosting", … } }
```

The payload's `description` and other long-text fields may be HTML or
Markdown; Clarity stores Markdown either way (see *Listing text is Markdown*).

A structured payload requires a **verified Clarity site for the URL's host**, so
no caller can inject a listing onto a domain it does not own, and the payload
goes through the same normalizer a crawl would use. Clarity also queues a
verification crawl of the public page, which stays the canonical source. A bare
`{ "url": … }` is simply an index request; `{ "url": …, "closed": true }`
withdraws the listing.

This is the boundary `OxyHQ/Mention#952` consumes. Mention keeps authoring,
applications and employer permissions; it writes nothing into Clarity's
database.

## SDK

```ts
import { ClarityClient } from '@clarity.surf/sdk';

const clarity = new ClarityClient({ apiKey: process.env.CLARITY_API_KEY });

const results = await clarity.jobs.search({
  query: 'React Native developer',
  locations: ['europe'],
  workplaceTypes: ['remote'],
  employmentTypes: ['full_time'],
  salary: { min: 60_000, currency: 'EUR', interval: 'year' },
  publishedAfter: '2026-09-01T00:00:00Z',
  limit: 25,
});

for (const job of results.data) {
  console.info(job.title, job.employer.name, job.source.canonicalUrl);
}
```

`clarity.jobs.get(id)`, `clarity.jobs.byUrl(url)`, `clarity.jobs.ingest(...)`,
`clarity.jobs.report(id, { reason })`, `clarity.jobs.stats()` and
`clarity.jobs.capability()` complete the namespace.

## Agents

`GET /jobs/capability` returns a tool descriptor — name, endpoint, parameter
schema, the permitted ranking signals, and the grounding rules — that Clarity's
Alia agent registers so a request like *"find remote React Native jobs in Europe
posted this week"* becomes a structured query. The descriptor states the rule
explicitly: a field missing from a result was not stated by the source and must
never be inferred, and the canonical source must always be shown.

## Portal

`clarity.surf/jobs` is a first-class vertical: query and location inputs,
workplace/employment/recency/salary filters, cursor pagination, and explicit
loading, error, empty and degraded states. Cards show title, employer, workplace
type, location, salary when stated, age, an evidence-grounded plain-text excerpt
and the source domain. The detail view renders the long-text fields as Markdown. The detail view leads with attribution — *Clarity indexed this
listing from `<domain>`; Clarity is not the employer and does not receive
applications* — and links out to the original. Clarity never presents itself as
the employer or the publisher of a listing it merely indexed.

## Operations

```bash
# Apply the Jobs projection migration
DATABASE_URL=postgresql://... bun run --filter @clarity/backend db:migrate -- \
  --target-database=clarity_ci --phase=pre

# Corpus health
curl -H "Authorization: Bearer $CLARITY_API_KEY" https://api.clarity.surf/v1/jobs/stats
```

The worker performs lifecycle maintenance and recrawl scheduling on its normal
loop; no separate scheduler is required.
