# Clarity

Clarity is a search product — the public web, jobs, news and markets — with an
assistant. The product is Clarity's; the assistant is an ordinary Alia agent.

```text
Expo client
  -> Express product API  -> PostgreSQL (Clarity's product)
  -> Alia, through @alia.onl/sdk, under the person's own Oxy session
       (the Clarity agent's conversation, paid by the person's Alia credits)
       -> Oxy capability ticket -> Clarity's catalogue at /_oxy/mcp
       -> Oxy inference -> Kaana
```

| Owner | Responsibilities |
| --- | --- |
| Clarity | The search index and its public/indexing platform, [Jobs](jobs), places, market quotes, news, [Experience](experience), suggestions, notifications, feedback, the plan catalogue, subscriptions and entitlements, and the [capability catalogue](assistant) that exposes them to agents |
| Alia | The Clarity agent (prompt, character, families, ceiling, feature gates), its conversations and sharing, memory, deep research, credits and checkout, usage and analytics, audit, triggers and channel bots |
| Oxy | Sessions, applications and their confined agents (ADR 0044), capability tickets and ceilings (ADR 0042), inference accounting and route authorization |
| Kaana | Provider-key custody, deployments, provider execution and failover within Oxy's signed order |

Clarity's backend uses PostgreSQL/Drizzle only. It has no provider adapter,
provider credential, route scoring or direct provider endpoint, and it never
calls Alia. Stripe, VAPID, Valkey and Oxy session configuration are
product/platform credentials, not inference provider keys.

Kaana is the sole hosted inference data plane. Its only canonical origin is
`https://kaana.ai`; Clarity never addresses Kaana through an `oxy.so` alias.
Chat reaches Kaana only through Alia, paid by the person. The one call Clarity
makes to Kaana itself is search embeddings: `POST https://kaana.ai/v1/embeddings`
through `@kaana.ai/sdk`, authenticated by Clarity's attested service token for
the `kaana.ai` audience (Kaana ADR 0002). That is Kaana's public API, never its
`/internal/` routes.

## Embeddings capability

Embeddings are off unless the deployment sets `CLARITY_EMBEDDINGS_ENABLED=true`,
which asserts that Kaana serves Clarity's embedding model
(`qwen/qwen3-embedding-8b`, 1024 dimensions) to Clarity's backend
application. Kaana's model catalogue is declared, not live, so it cannot answer
that question; the setting does.

- **Off:** the route is never called. Indexing stores chunks without
  embeddings, `POST /v1/search` and `POST /v1/jobs/search` rank lexically and
  answer `degraded: { from: 'hybrid', to: 'lexical', reason:
  'embedding_route_unavailable' }`, and `mode: 'semantic'` answers `503
  semantic_unavailable`. The process logs once that embeddings are off.
- **On:** chunks and queries are embedded. A query is embedded on its own, when
  it is asked. Chunks never hold up indexing: a document's chunks are stored
  unembedded (lexically searchable at once) and queued, and the queue
  (`packages/backend/src/search/embedding-queue.ts`) embeds chunks from many
  documents per request and writes the vectors into the stored chunks. A
  request carries up to 128 chunks and 65,536 estimated tokens (Kaana's
  UTF-16 length / 4 + 1 per input); a full batch is sent at once, a partial one
  once its oldest chunk has waited 10 seconds, and never more than one request
  every 2 seconds (Oxy's machine lane allows the credential 60 a minute, shared
  with queries). One request per document cost ~70 grants a minute and was
  refused past 60 (2026-10-16).
- **Failures:** a failed call (Kaana error, timeout, malformed answer) degrades
  a query exactly as above and is logged at most once every five minutes with
  the number of failures since the last log line. A failed chunk request backs
  off the whole queue — for Kaana's `Retry-After`, and at least 5 seconds,
  doubling to 5 minutes while failures continue. Rate-limited, unavailable and
  timed-out chunks stay at the head of the queue and are sent again after the
  back-off; chunks of any other failure are dropped and stay unembedded. The
  SDK does not retry queued calls: the queue's back-off is the only one.
- **Turning it on later, or a restart:** chunks without a current embedding are
  `unembedded` (`documentChunkState`), so the next recrawl or feed delivery of
  each document queues them again without rewriting anything else.

## Canonical product identity

Every value is an opaque primary key, matched byte for byte, never discovered by
name, list position or order (`packages/backend/src/lib/clarity-identity.ts`).

| Record | Canonical value |
| --- | --- |
| Clarity project account (owns the agent) | `01a0646a-078f-7f53-848d-a0f82d9f7fa6` |
| Clarity agent (Alia), opened by the frontend | `01a0646a-078f-7642-95ef-439952f4f3f9` |
| Clarity agent's bot account (confined to Clarity) | `01a0646a-078f-7120-a993-a03c180c81b0` |
| Backend service application | `01a0648b-8d73-70ad-8e67-1c07ddc5eb6e` |
| Backend task role | `arn:aws:iam::237343248947:role/oxy-clarity-task` (`wl_1553bb11eb957512b3cdc956`) |
| Public sign-in application | `01a0646a-2382-74a3-a795-788924d55722` |
| Public sign-in client ID | `oxy_dk_75cdd9996d19362e15ddedcc5ab0f4fb310de8d7b5e8523a` |

The backend's service token carries exactly `user:read`, `inference:invoke`
(search embeddings), `catalogs:write` (with the application capability
`catalog:clarity`), `capabilities:read` and `capability-audit:write`; anything
else is refused (`clarity-service-auth.ts`). The public application has only
`user:read`.

## Fail-closed state

`/health/ready` and every product HTTP route and Socket.IO handshake stay closed
until PostgreSQL is reachable, the data snapshot is attested (`cutover` or
`fresh_install`) and the process can attest its service identity. The MCP lanes
are not behind that gate — their authority is the ticket or the OAuth token —
and `/_oxy/mcp` answers 503 until this process's catalogue registration
succeeds.
